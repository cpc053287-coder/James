# Playbook:修改代碼

觸發:任何會 Edit / Write 既有檔案,或新增代碼檔案的任務。

## 小步循環(核心流程)

1. **定位**:用 Grep / Glob 找到確切要改的位置。動手前,先列出「本次會動的檔案清單」。
   - 找不到預期中的檔案或符號?先假設是自己拼錯或理解錯,換 2–3 組關鍵字重搜;
     超過 15 分鐘仍找不到 → 走 `stuck.md`,不要開始「大概是這裡」式的修改。
2. **讀**:Read 每一個要改的區段,以及它的呼叫端(鐵律 1)。
3. **一次改一個邏輯單位**(一個函式、一個 bug、一個欄位),改完立刻跑「最窄的檢查」:
   - 有單元測試 → 只跑該檔案 / 該案例的測試
   - 沒有測試 → 跑型別檢查或 lint;或寫 3 行臨時腳本呼叫看看(放 scratchpad,不進 repo)
   - 檢查紅了 → 立刻修好再繼續。**不准帶著紅燈改下一處。**
4. 重複步驟 3,直到清單上的檔案都改完。
5. **收尾**:跑完整驗證(見 `verification.md`)→ `git diff` 逐段對照使用者請求(鐵律 5)→
   有對不上的改動:撤掉,或移入 `todo.md`。

## 規模熔斷

以下任一成立、且使用者沒有明示要大改 → 停下,在回覆中說明原因並提出分階段方案,先只做第一階段:

- diff 超過約 300 行,或動到超過 5 個檔案
- 需要改對外介面(函式簽名、CLI 參數、HTTP API、資料 schema)
- 需要新增依賴(新增依賴一律要在回覆中說明理由,以及「不加依賴的替代方案為何不夠好」)

## 風格判準(不要用你自己的預設)

寫新代碼之前,打開同目錄裡最相近的既有檔案,模仿它的:命名、註解密度、錯誤處理方式、import 順序。

- 例:既有代碼不寫行內註解 → 你也不寫;既有代碼用 snake_case → 你不准寫 camelCase。
- 整個 repo 都沒有可模仿的代碼 → 用該語言官方風格指南的預設值。

註解只寫「代碼本身表達不出來的約束」(為什麼不能用更直覺的寫法、外部系統的限制)。
不寫「這行在做什麼」的翻譯式註解,不寫「本次修改說明」式的註解——那是給 reviewer 的話,放回覆裡。

## 常見翻車案例(前人踩過,勿重蹈)

- ❌ 連改 5 個檔案才第一次跑測試,紅了 12 個,分不出是哪一步弄壞的。
  → 照步驟 3 每步跑窄檢查,就不會發生。
- ❌ 順手把旁邊的舊式寫法「現代化」,diff 膨脹三倍,reviewer 找不到重點。
  → 鐵律 5:記入 todo.md,不動手。
- ❌ 憑印象呼叫 `dayjs.duration()`,但專案根本沒註冊 duration plugin,執行才炸。
  → 鐵律 7:寫下任何非本 repo 定義的 API 前,先 grep import 或查官方文件。
