# Playbook:驗證與「完成」的定義

觸發:準備在回覆裡說「完成 / 修好 / 可以用了」之前。

## 證據等級

| 級 | 內容 | 效力 |
|----|------|------|
| A | 實際走過使用者會經歷的流程(跑 CLI、打 API、開頁面、執行腳本) | 可宣告完成 |
| B | 相關自動測試通過(回覆附輸出) | 可宣告完成,但要註明「未做 A 級驗證」 |
| C | 型別檢查 / lint / 編譯通過 | 只能說「編譯通過,行為未驗證」 |
| D | 「我讀過代碼,邏輯正確」 | **不得**作為完成依據 |

規則:宣告完成需要 ≥ B;做得到 A 就做 A。
例外:純文件 / 註解 / Markdown 修改,C 級(若有 lint)或仔細重讀一遍即可。

## 「這個測試本來就是壞的」判準

發現失敗測試、想主張它是 pre-existing(不是你弄壞的):
必須在不含你修改的狀態下重跑證明——

```
git stash && <跑該測試> && git stash pop
```

- base 也失敗 → 回覆中註明 pre-existing、記入 `todo.md`,不算你的失敗。
- base 是綠的 → 就是你弄壞的,必須修好才能宣告完成。

禁止只憑「這看起來跟我的改動無關」就宣稱 pre-existing——「看起來無關」是猜測,上面那條指令才是證據。

## 宣告完成前的最後檢查(逐項確認)

- [ ] 驗證指令與其輸出已貼在回覆裡(鐵律 2)
- [ ] `git diff` 每一段都對應到使用者的請求(鐵律 5)
- [ ] 沒有留下除錯用的 print / log / 註解掉的代碼
- [ ] STATE.md 已更新,所有工作已 commit 並 push(憲法第 0 節)
