# Playbook:除錯

觸發:任務是「修 bug / 壞了 / 報錯」,或你自己在本 session 中改壞了東西。

## 順序(不得跳步)

1. **重現**:先取得一個穩定重現的最小步驟(一條指令或一個測試)。
   - 無法重現 → 不准開始改代碼。缺環境資訊或觸發條件就向使用者要
     (這符合憲法第 2 節「該問」的判準 (c))。
2. **讀完整錯誤訊息**:從第一行讀到最後一行,包含 stack trace 的最底層與所有 `Caused by:`。
   錯誤訊息指出的檔案與行號,優先於你的任何猜測。
3. **定位**:逐步縮小範圍。可用手段(按成本由低到高):
   - 讀 stack trace 指到的代碼與其呼叫端
   - 「以前是好的」→ `git log -p -- <file>` 找嫌疑 commit,必要時 `git bisect`
   - 在懷疑點加 print / log,重跑重現步驟,觀察實際值
4. **寫出因果,才准動手**:必須能寫出一句
   「因為 A(`檔案:行號`),所以出現 B(觀察到的症狀)」。
   寫不出這句 = 定位還沒完成,回到步驟 3。這句話之後要放進給使用者的回覆裡。
5. **最小修復**:只修因果鏈上的東西。不順手重構、不順手改風格(鐵律 5)。
6. **驗證**,三件缺一不可:
   - (a) 步驟 1 的重現步驟現在通過
   - (b) 相關既有測試沒有變壞
   - (c) 若這個 bug 值得防回歸(修的是邏輯而非錯字),補一個「修復前會失敗」的測試

## 禁止

- 還沒重現就改代碼(「我猜是這裡」)。
- 一次套用多個猜測性修改。套一個、測一個;混在一起你將無法知道是哪個生效。
- 只讀錯誤訊息的第一行。真正原因常在 trace 最底部。
- 用 try/except、`|| true`、skip 測試把症狀蓋掉。蓋掉症狀 ≠ 修好;
  除非使用者明確要求「先讓它不要炸」。

## 熔斷

同一個症狀,兩次「以為修好了」但重現步驟仍然失敗 → 停,走 `stuck.md`。
第三次盲試幾乎總是在浪費時間與使用者的錢;兩次失敗代表你的因果假設是錯的,
需要的是新資訊,不是新嘗試。
