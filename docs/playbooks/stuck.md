# Playbook:卡住時

觸發(任一成立就算「卡住」,不要拖到情況更糟才承認):

- 同一個問題,兩次修復嘗試都失敗(鐵律 6)
- 搜尋一個「應該存在」的檔案 / 符號 / 設定,超過 15 分鐘還沒找到
- 需要的資訊只有使用者有(帳號、偏好、外部系統的狀態、業務規則)
- 使用者的要求與鐵律衝突,或兩條規則互相衝突

## 動作(依序)

1. **停止嘗試。** 不要開始第三次盲試。
2. 寫「卡住報告」,直接放進給使用者的回覆:

   ```
   嘗試 1:<做了什麼> → <結果 / 錯誤訊息原文>
   嘗試 2:<做了什麼> → <結果 / 錯誤訊息原文>
   目前最佳假設:<一句話>
   已排除:<確定不是什麼,附依據>
   需要:<具體要什麼才能繼續——一個決定 / 一段資訊 / 一個權限>
   ```

3. 把報告摘要寫進 STATE.md 的「地雷與教訓」,commit + push。
   就算這個任務失敗了,下一個 session 也不必重踩同樣的坑——這本身就是產出。
4. 能用 AskUserQuestion 就用:選項要具體、互斥、附上你建議哪個與理由。
   不能用(使用者不在線上)→ 在回覆第一行標 **BLOCKED**,說清楚等什麼。

## 判斷句(具體化的「心法」)

- 「帶著清楚的問題停下」的價值 > 「帶著錯誤的自信前進」。
- 自問:如果使用者此刻就站在旁邊看,他會說「繼續試」還是「你先問我」?
  兩次失敗之後,答案幾乎總是後者。
- 卡住報告寫得好的判準:使用者(或下一個 session)讀完後,
  **不需要重做你做過的任何嘗試**,就能直接做決定或接手。
